# Decision log

Why this repository exists, what it is made of, and the order it is being
built in. Newest decisions at the top of each section. Dates are when the
decision was made.

## 2026-09-23 — Port HTDemucs to pure Rust, no ONNX at runtime

### Context

Wavey separates tracks on device with a Core ML HTDemucs package
(`StemSeparator.swift`). The question was whether the same work can
run on a server — the service already fans out ECDC encoding one independent
segment per Lambda invocation — and whether the seam can be shared so the
phone and the cloud cannot disagree.

The ECDC work the ECDC cloud-offload work set the shape: one
independent segment per invocation, fan out, concatenate. EnCodec's segments
are fixed-context, so they are byte-exact and order-free. HTDemucs is not: its
segment is the model's own inference unit and its output depends on the
overlap plan, so the plan is part of the format and must be pinned once.

### Decision: a separate private repo, `wavey-ai/stemsplits`

It owns everything stem-related: the STFT contract, the chunk plan, the
overlap-add seam, the model weights and inference, the segment API, and
deployment. This mirrors `wavey-ai/encodec-rs` (the ECDC codec) and
`wavey-ai/beatmaker` (the shared composition engine). Wavey calls it; it
does not keep a second copy of the seam.

### Decision: no ONNX at runtime

`encodec-rs` removed ONNX from the shipping path: it extracts weights and
drives its own C SIMD kernels, with a portable Rust reference beside them and
FP contraction pinned off (`-ffp-contract=off`) so backends agree. We follow
that rule. PyTorch and ONNX are **oracles for parity tests**, not runtime
dependencies. The plan is portable Rust first, then kernels for the hot ops.

### Decision: the STFT is a faithful port, quirks included

`stemsplits-stft` reproduces `StemSeparator.swift` exactly, because the Core
ML model was converted against it:

- forward is the true `rfft` of a periodic-Hann-windowed, reflect-padded
  signal, scaled by `1/sqrt(fft_size)`;
- the Nyquist bin is **dropped** (Demucs keeps `fft_size / 2` bins);
- the inverse is the true inverse DFT with Nyquist forced to zero;
- overlap-add accumulates the squared window over **every** inverse frame,
  including the two leading and two trailing zero frames that carry no audio.

The last one is not tidiness: it changes the normalisation at the edges.
The low forward-then-inverse reconstruction SNR (~34 dB at the shipped
geometry) is expected — it is Demucs' lossy pair, not a bug.

Parity is proven against a golden generated by `tools/oracle-stft/main.swift`,
a copy of the Swift/vDSP implementation. The Rust matches it to ~2e-7.

### Decision: the chunk plan and seam live here, pinned

`stemsplits-demucs` holds `StemKind`, the `ChunkPlan` (segment 343,980 frames,
overlap 0.25, stride 257,985) and the triangular overlap-add. Tests prove a
constant reconstructs across seams and, importantly, that **streaming flush
equals batch flush** — the property that makes streaming stems possible with
one-segment lookahead.

### The model

The on-device Core ML package is standard `htdemucs` (Demucs v4, checkpoint
`955717e8`), the MIT-licensed 4-stem hybrid transformer. The Core ML graph is
an ML Program with **f16** weights (`tencoder_0_conv_weight_to_fp16`), 104.6 MB
— the same model, smaller storage, not a different model. The PyTorch
checkpoint is therefore the correct source of weights and the oracle for
activations. The config is pinned in
`tools/reference/demucs_config.json`.

Shape: 48-channel convolutional encoder and decoder over both a spectrogram
branch (complex-as-channels, `cac=true`) and a waveform branch, joined by a
5-layer cross-domain transformer at 512 channels (`bottom_channels=512`).
41,984,456 parameters. `norm_starts=4` with `depth=4` means the encoder and
decoder layers carry **no** GroupNorm; the GroupNorms in the graph come from
DConv and the transformer's `norm_out`.

### The forward, exactly

1. `_spec`: reflect-pad by `hop/2*3`, STFT (normalized), drop Nyquist, take
   `le = ceil(length/hop)` frames. Our `stemsplits-stft` reproduces this.
2. Normalise the CaC magnitude per sample (mean/std over channels, freq, time)
   and the waveform per sample (mean/std over channels, time). This
   normalisation is **inside** the Core ML graph, so the Rust must do it too.
3. Encoder: 4 freq layers (Fr 2048→512→128→32→8) and 4 time layers. A
   frequency embedding is added after layer 0.
4. Upsample both branches 384→512, run the cross-transformer: layers 0,2,4 are
   self-attention on each branch, layers 1,3 cross-attend (freq queries time,
   time queries the pre-update freq). Then downsample back 512→384.
5. Decoder: 4 freq layers and 4 time layers with skip connections.
6. Output the freq branch as 16 channels (4 stems × 2 audio channels ×
   real/imag) and the time branch as 8 channels (4 stems × 2 channels), both
   denormalised. The caller does `time + iSTFT(freq) * sqrt(fft_size)`.

### Decision: build the port layer by layer, against dumped activations

`tools/reference/reference_stems.py` runs the reference on the fixed
deterministic segment and dumps the stems and activations:

```
stems                  (1, 4, 2, 343980)
encoder.0              (1, 48, 512, 336)
encoder.1              (1, 96, 128, 336)
encoder.2              (1, 192, 32, 336)
encoder.3              (1, 384, 8, 336)
channel_upsampler      (1, 512, 2688)
channel_upsampler_t    (1, 512, 1344)
```

Each Rust module is checked against the matching activation before the next is
started, in this order:

1. encoder stack — conv2d/conv1d, GroupNorm, GELU, GLU, DConv, frequency
   embedding;
2. cross-transformer — linear, LayerNorm, multi-head attention, `norm_out`,
   sinusoidal positional embeddings (2D for freq, 1D for time), LayerScale;
3. decoder — conv_transpose2d, skips, final CaC reshape;
4. the full segment: stems in, compared to the reference stems per stem.

Parity is tolerance-based, not byte-exact: the device runs f16, the reference
runs f32, and our Rust starts in f32. The first meaningful number is the
arm64 CPU real-time factor for one 7.8-second segment — that decides whether
cloud stems beat the phone (see `bench/README.md`).

```

crosstransformer.t  2.6e-6
```

`transformer.rs` holds the 2D/1D sinusoidal positional embeddings, multi-head
attention (self on layers 0/2/4, cross on 1/3), LayerNorm, LayerScale

### The baseline: ONNX Runtime, PyTorch, and the naive Rust port

`tools/reference/export_onnx.py` exports the same I/O contract (mag +
waveform in, freq/time out) to ONNX; `bench_onnx.py` measures it and checks
it against PyTorch. `cargo run --release -p stemsplits-htdemucs --bin bench`
times the Rust port. One 7.8 s segment, on this machine:

| implementation | threads | s/segment | RTF | artifact |
| --- | ---: | ---: | ---: | ---: |
| Rust, naive scalar | 1 | 343 | 44.0 | 987 KB binary |
| ONNX Runtime | 1 | 20.4 | 2.61 | 174.3 MB onnx + 58.4 MB lib |
| ONNX Runtime | 8 | 8.79 | 1.13 | |
| PyTorch CPU | 8 | 8.49 | 1.09 | |

Accuracy against PyTorch, on the same input:

| implementation | freq_output | time_output |
| --- | ---: | ---: |
| Rust port | (end to end) 3.1e-6 | |
| ONNX Runtime | 5.6e-4 | 5.0e-5 |

Two things follow.

**Smaller: yes.** The Rust artifact is a 987 KB binary with no ONNX Runtime
(58.4 MB here, ~15–20 MB for the shared library alone). The f32 weights are
168 MB either way, so the honest total is 987 KB + weights against 174.3 MB +
58.4 MB. An f16 bundle halves our weights, matching the device.

**Faster: no, not yet.** We are 17× slower than ONNX Runtime on one thread
and 40× slower than the 8-thread run. Nothing is SIMD, nothing is threaded,
and the attention materialises its score matrix. The port is also *more*
accurate than the ONNX export relative to PyTorch (3e-6 against 5.6e-4),
which suggests the export is folding constants more aggressively.

**The larger finding stands.** EnCodec's ECDC runs at RTF 0.04 on Lambda
because its kernel is small and hand-optimised. HTDemucs is a ~42 M-parameter
transformer; even optimised CPU implementations land near RTF ~1 on many
cores. Cloud stem separation is **not** obviously the same win as cloud ECDC,
and streaming stems inherits that cost. The bench exists to make this
measurable before more is built on the assumption.

### The kernel pass: single-threaded, to RTF 1.6

Threading is deferred: a Lambda at 1769 MB gets a single vCPU, so it would
only pay on a larger function. The work went into the single-threaded
kernels instead, each step measured with `bench`:

| change | RTF |
| --- | ---: |
| naive scalar | 44.0 |
| blocked matmul, four independent accumulation chains | 20.7 |
| conv2d as im2col + matmul (the decoder's 3x3 rewrites were ~28 GFLOP of serial accumulation) | 13.9 |
| conv_transpose1d/2d as matmul + scatter | 7.65 |
| `Linear` transposes its weight so the matmul's inner loop is the vectorisable one | 3.28 |
| C NEON micro-kernel, four rows × one vector, k innermost | 2.26 |
| micro-kernel widened to eight columns with `vmlaq_n_f32` | **1.61** |

The lesson repeated from `encodec-rs`: **the Rust scalar loop does not
vectorise.** A reduction cannot be reassociated without changing the result,
and the compiler will not do it, so neither blocking nor `target-cpu=native`
helped until the SIMD was explicit. The C kernel (`kernels/gemm.c`) is
compiled by `build.rs` with AVX2/FMA on x86 and NEON on aarch64; its
per-output accumulation order is unchanged, so only FMA contraction moves the
result, inside the parity tolerance (stems stay at 2.99e-6 against PyTorch).

At RTF 1.61 the port is now faster than ONNX Runtime on one thread (2.61) and
close to ONNX Runtime on eight (1.13) and PyTorch on eight (1.09), while
single-threaded. The artifact remains a ~1 MB binary with no ONNX Runtime.
